# HabitHamster ML — индивидуальная работа Гогиты Мандзулашвили

Самостоятельный Python-пакет, выделенный из группового HabitHamster.
Источник: https://github.com/W1llAnn/Project_workshop_2s, commit
`95453d40777323f396a979cb30cbc3282d981993`.
Исходные авторы — команда HabitHamster; это рефакторинг групповой работы,
а не заявление об авторстве исходного алгоритма. Общий backend не изменяется.

## Воспроизводимый запуск

Нужны Python 3.12 и Poetry 2.2.1. Из корня репозитория:

```bash
python -m pip install poetry==2.2.1
poetry -C ml sync --with dev
poetry -C ml run pre-commit install
poetry -C ml run habit-ml demo
poetry -C ml run pytest tests
poetry -C ml run pre-commit run --all-files
```

Windows: команды те же, выполняются в PowerShell при доступном Python 3.12.
Активация окружения необязательна: poetry run использует его автоматически.
Не коммитить .venv, сырые данные, модели и секреты. Создание окружения на новой
машине — `poetry -C ml sync --with dev`; зависимости берутся из poetry.lock.

Форматирование и сборка:

```bash
poetry -C ml run ruff check --fix src tests
poetry -C ml run ruff format src tests
cd ml
poetry build
cd ..
```

Контейнер (из корня): `docker build -t habithamster-ml ml`;
`docker run --rm habithamster-ml` запускает синтетическое демо.

## Устройство модуля

- data.py — CSV и проверки схемы, типов, статусов и дублей.
- features.py — общие признаки для обучения и предсказания.
- model.py — LightGBM, сохранение/загрузка, рекомендации, cold start.
- onboarding.py — исходный каталог и рекомендации по анкете, cosine similarity.
- cli.py — команды demo, train, recommend.
- tests/ — реальные проверки обучения, сохранения, CLI и граничных случаев.

Исходный обучаемый алгоритм сохранён по смыслу: статусы done/partial/skipped/missed
кодируются 1/0.6/0.1/0, взаимодействия взвешиваются по давности с масштабом 30 дней,
цель — weighted_score >= 0.7. Шесть признаков: уровень, серия, средний успех,
сложность привычки, совпадение тегов и результат похожих пользователей.

Изменения поведения: исключение соседа по user_id вместо позиции строки;
единый расчёт признаков; все теги вместо случайного первого;
удалён случайный шум из вероятностей; reference date берётся из данных;
min_child_samples=5 для небольших учебных выборок; сохранение атомарное; проверяются два класса; вектор спорта принимает строку и список.

## Свои данные

Экспортируйте в CSV данные активных привычек из группового проекта.
logs.csv: user_id, habit_id, status, log_date, habit_title, target_type,
target_value, user_level, current_streak. Одна строка на habit_id/log_date;
каждый habit_id принадлежит одному пользователю. tags.csv: habit_id, tag_slug,
по одной строке на тег. Даты ISO, числовые значения неотрицательные целые.

```bash
poetry -C ml run habit-ml train --logs logs.csv --tags tags.csv --model ml/artifacts/model.joblib
poetry -C ml run habit-ml recommend --logs logs.csv --tags tags.csv --model ml/artifacts/model.joblib --user 1
```

Загружайте только собственные доверенные joblib-артефакты.
В модуле нет соединения с БД и встроенного планировщика. CSV — явная граница
интеграции. В групповом приложении обучение запускалось Celery каждые 30 минут,
а рекомендации — ежедневно в 12:00 UTC; здесь запуск явный через CLI.

## Ограничения модели и мониторинг

Работа закрывает инженерные требования учебного задания, но не доказывает
качество рекомендаций на реальных пользователях. Демо синтетическое;
нет оценки на отложенной выборке. Исходный target и агрегаты строятся на одной
истории, поэтому для честной оценки нужны признаки до временной границы,
результаты после неё и временной holdout. Habit ID индивидуален владельцу,
поэтому матрица взаимодействий разреженная; CF часто возвращает fallback 0.5.
Для развития нужен общий каталог шаблонов привычек и реальные взаимодействия.

Реализован logging числа логов, пар и признаков при обучении. Автоматического
мониторинга качества/drift нет. Перед реальным внедрением следует проверять
свежесть/полноту данных, время обучения, долю fallback, ошибки предсказания и
метрики ranking на holdout; новую модель публиковать только после этих проверок.

## Сверка с презентациями преподавателя

Просмотрены все три презентации. Дополнения после сверки:

- «Основы MLOps», слайд 13: лимит 79 символов. Настроены Ruff formatter
  и проверка E501; включены проверки E/W, F, I, B.
- Слайды 55 и 59: окружение не хранится в Git; poetry.lock фиксирует
  зависимости; кэш CI привязан к ОС, архитектуре, Python, Poetry и hash lock.
- Слайд 69: CI проверяет Linux, Windows и macOS. На macOS устанавливается
  libomp для LightGBM. Пока локально проверен Linux; матрица будет выполнена
  после push в форк. Для локального macOS сначала `brew install libomp`.
- Black/Flake8 в лекции — примеры инструментов. Здесь Ruff выполняет роли
  форматтера, линтера и сортировщика импортов; Poetry и pre-commit сохранены.
- GitLab/Merge Request показаны как процесс разработки. Для GitHub используется
  эквивалент: отдельная feature-ветка, Pull Request и GitHub Actions.
- «Оркестрация контейнеров», слайд 27: пункты 2–4 совпадают с заданием.
  Kubernetes не указан как обязательная часть этих пунктов.
- Презентация об актуальности MLOps раскрывает drift, monitoring и ROI;
  их внедрение не является отдельным требованием выбранных пунктов.
  Ограничения текущего мониторинга честно описаны выше.

Вторая презентация, слайд 71, формулирует пункт 4 как интеграцию в репозиторий
команды; третья, слайд 27 — как интеграцию виртуального окружения в Git.
Работа готовится в личном форке по согласованному плану. Для требования о
командном репозитории при необходимости можно показать PR с изменениями,
но слияние в оригинал требует отдельного решения команды.

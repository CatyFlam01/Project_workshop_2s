Модуль `onboarding.py` отдельно подбирает привычки по анкете через cosine similarity;
это другой механизм, и результаты его работы не являются метриками LightGBM.

### Алгоритм обучения

Статусы выполнения преобразуются в оценки: `done=1`, `partial=0.6`,
`skipped=0.1`, `missed=0`. Для каждой пары пользователь–привычка вычисляется
среднее с весом `exp(-days / 30) + 0.01`, где `days` — число дней от записи
до максимальной даты в переданных логах. Целевая переменная:
`y = 1`, если взвешенная оценка не ниже `0.7`, иначе `0`.
Это метка исторического выполнения, а не измеренная реакция на новую рекомендацию.

Параметры `LGBMClassifier`: `n_estimators=100`, `max_depth=4`,
`learning_rate=0.1`, `class_weight="balanced"`, `random_state=42`,
`n_jobs=1`, `min_child_samples=5`. Минимум для обучения: 50 записей,
30 пар пользователь–привычка и наличие обоих классов. Эти проверки
не гарантируют статистическую достаточность данных.

## 2. Intended Use — назначение и применение

**Задача:** ранжировать привычки-кандидаты для пользователя приложения
HabitHamster на основе его истории и характеристик привычек.
Предполагаемая польза — облегчить выбор подходящей привычки и поддержать
регулярное выполнение. Рост удержания, конверсии или дохода пока не измерен.

**Пользователи:** разработчики и аналитики проекта; после проверки качества —
пользователи приложения, которые самостоятельно принимают или отклоняют совет.
Сейчас модуль запускается явно через CLI и CSV, независимо от Django.

**Вне области применения:** медицинские назначения, диагностика, оценка
здоровья или личности, обязательные решения о пользователе. Значение `score`
нельзя представлять как доказанную вероятность будущего успеха.

### Входные данные

| Источник | Поля и смысл |
| --- | --- |
| `logs.csv` | `user_id`, `habit_id` — идентификаторы; `status` — выполнение; `log_date` — дата; `habit_title` — название; `target_type` — `check/minutes/count`; `target_value` — цель; `user_level` — уровень; `current_streak` — серия выполнения |
| `tags.csv` | `habit_id`, `tag_slug` — теги привычки, одна строка на тег |
| Запрос | Идентификатор пользователя; `top_k=5`, `min_score=0.5` по умолчанию в Python API |

В логах обязательные поля не должны быть пустыми; числовые значения —
неотрицательные целые; даты приводятся к UTC. Дубликаты `habit_id/log_date`
отклоняются, одна привычка принадлежит одному пользователю.
Валидация тегов ограничена наличием колонок: отдельной полной проверки
ссылочной целостности и дубликатов тегов нет.

Шесть признаков:

| Признак | Расчёт |
| --- | --- |
| `user_level` | Средний уровень пользователя по его логам |
| `user_streak` | Максимальная серия по его логам |
| `user_avg_score` | Средняя оценка статуса по его логам |
| `habit_difficulty` | `min(target_value × коэффициент / 50, 1)`; коэффициенты: check=1, minutes=0.5, count=1.5 |
| `tag_match` | Пересечение тегов пользователя и кандидата / объединение; при пустом объединении 0.5 |
| `cf_score` | Средняя положительная оценка кандидата среди до пяти соседей по cosine similarity; при отсутствии оценок 0.5 |

### Выходные данные

Список до `top_k` объектов: `habit_id`, `habit_title`, `score`, `explanation`.
Для пользователя с историей `score` — результат `predict_proba` для класса 1;
кандидаты — привычки других пользователей из переданных логов. Свои привычки
исключаются; применяется порог и сортировка по убыванию score.
При равенстве score порядок определяется `habit_id`. Список может быть пустым.

Для неизвестного пользователя классификатор не используется: возвращаются
привычки с высоким средним выполнением. Это fallback, названный в коде
`popular habit`, но он ранжирует по среднему score, а не по числу пользователей.
Его score не является вероятностью LightGBM. Текст `shared interests` либо
`personalized` — эвристическая подпись, не SHAP и не причинное объяснение.

## 3. Factors — факторы качества

Значимы длина и свежесть истории, уровень и серия пользователя, тип и сложность
цели, наличие тегов, категория привычки и режим cold start. Качество следует
оценивать раздельно по этим группам и их пересечениям, например короткая
история × сложная привычка. Границы групп определяются до оценки на реальных данных.

Пол и возраст не входят в признаки; это не доказывает отсутствие смещения.
Демографический состав пользователей и результаты fairness-анализа неизвестны.
Для анализа защищённых групп нужны обоснование сбора, согласие и достаточный
размер групп; данные для такого анализа сейчас не предоставлены.

## 4. Metrics — метрики и пороги

**Независимые метрики качества сейчас не вычислены.** Ниже приведён план оценки,
а не результаты существующего оценочного pipeline.

| Метрика | Что проверяет и как использовать |
| --- | --- |
| ROC-AUC | Разделение классов будущего выполнения при наличии обоих классов в holdout |
| Precision, Recall, F1 | Ошибки при заранее выбранном пороге классификации; вместе с балансом классов |
| NDCG@5, Precision@5 | Релевантность и порядок рекомендованных привычек при наличии наблюдаемого отклика на кандидатов |
| Coverage@5, доля пустых ответов | Охват допустимого каталога и доступность рекомендаций |
| Доля fallback | Частота работы без персонализированного предсказания |
| Принятие рекомендаций, выполнение, удержание | Бизнес-эффект в эксперименте относительно базового подбора; сейчас не измерен |

Порог `0.7` задаёт историческую метку. Порог `0.5` фильтрует рекомендации;
это разные величины. Порог допуска модели в production пока не установлен.
Для оценки неопределённости предлагается bootstrap по пользователям и несколько
временных окон, с указанием размеров выборок и доверительных интервалов.
Ранжирование следует сравнить с текущим fallback и простым контентным baseline
на одинаковых кандидатах. ROC-AUC сам по себе не подтверждает пользу рекомендаций.

## 5. Evaluation Data — данные оценки

Реальная независимая тестовая выборка не предоставлена. `demo_data()` создаёт
400 логов, 10 пользователей, 40 привычек и 40 строк тегов за 01–10.01.2026.
После агрегации — 40 пар, 20 положительных и 20 отрицательных меток.
Статусы искусственно чередуются по номеру привычки; это проверка интеграции,
а не репрезентативная выборка реального поведения.

План корректной оценки: зафиксировать временную границу; строить признаки и
матрицу взаимодействий только по прошлому; формировать целевую переменную по
следующему окну; отделить подбор параметров от финального теста. Для рекомендаций
новых привычек отдельно нужны показы и отклики на общий каталог. Отсутствие
записи об отклике нельзя автоматически считать отрицательной меткой.

## 6. Training Data — обучающие данные

В локальном демо используется описанный выше синтетический набор. Пользовательский
CSV для реального обучения должен содержать историю активных привычек HabitHamster.
Реальные объём, период, происхождение выгрузки, согласия и распределения классов
не установлены. Версия синтетических данных задаётся `demo_data()` в указанном
commit; для реальной выгрузки потребуются идентификатор версии и контрольная сумма.

Сейчас обучение использует все переданные данные без train/test split.
Цель и признаки строятся на одной истории: в частности `user_avg_score`
содержит оценки целевой привычки. Есть риск утечки целевой информации.
Метрики на обучающей выборке нельзя использовать как доказательство обобщения.

## 8. Ethical Considerations — этика и риски

- Логи, названия привычек и теги могут раскрывать личные интересы. Идентификатор
  вместо имени не гарантирует анонимность; сырые данные и модели не публикуются.
- Текущий кандидат содержит название чужой привычки. Перед пользовательским
  внедрением требуется общий обезличенный каталог и проверка допустимости показа.
- Активные пользователи и частые категории могут преобладать; малой истории
  недостаточно для надёжной персонализации. Нужны анализ групп и возможность отказа.
- Рекомендации должны оставаться добровольными. Пользователь должен понимать
  ограничения; медицинская безопасность рекомендаций не подтверждена.
- Joblib содержит сериализованную модель и пользовательскую матрицу.
  Загружать можно только доверенные артефакты с ограничением доступа.

## 9. Caveats and Recommendations — ограничения и развитие

1. Одна привычка принадлежит одному пользователю. Строки матрицы имеют
   непересекающиеся habit_id, поэтому для валидных данных cosine similarity
   разных пользователей равна нулю. При обучении CF для собственной привычки
   равен fallback 0.5: другие пользователи не имеют её оценок. При inference
   код не отбрасывает соседей с нулевым сходством и может использовать оценку
   владельца кандидата, если тот попал в первые пять соседей, либо fallback 0.5.
   При равном сходстве порядок соседей зависит от user_id. Для осмысленного CF
   нужен общий каталог.
2. Обучение идёт на собственных привычках, а inference — на чужих кандидатах:
   это различие распределений требует отдельной проверки.
3. Сохранённая матрица относится к обучению, а текущие логи могут обновляться.
   Версии данных, матрицы и признаков должны быть согласованы.
4. Score не калиброван; `class_weight="balanced"` не является fairness-ограничением.
5. Автоматические drift-мониторинг, переобучение, реестр моделей и публикация
   в приложение в самостоятельном модуле не реализованы.
6. До реального запуска нужны временная оценка без утечки, безопасный каталог,
   сравнение с baseline, проверка групп, критерии допуска и процедура отката.
